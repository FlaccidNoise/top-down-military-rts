## 1. Theater model (spine — final form)

The theater domain owns the spine; synthesis applies R1-R9. All coordinates are INTEGER metres (`Math.round` at every emission point). The Theater is IMMUTABLE after generation — zero owner fields, zero scars, zero mutable state. Every mutable field lives in Front V2.

```ts
// src/strategic/theater.ts
export type Vec = { x: number; y: number };                    // integer metres
export type TerrainClass = 'farmland' | 'bocage' | 'forest' | 'marsh' | 'settlement';
export type NodeKind = 'town' | 'village' | 'crossroads' | 'junction' | 'bridge' | 'ford' | 'halt';
export type MoveClass = 'highway' | 'road' | 'track' | 'rail';
export type Rank = 0 | 1 | 2;                                   // derived: display weight/label priority

export interface TheaterNode {
  id: number;                    // dense 0..n-1, generation-ordered, frozen (R23)
  pos: Vec;
  kind: NodeKind;
  name: string;                  // deterministic Norman toponym (T_NAMES)
  regionId: number;
  crossing: { riverId: number; kind: 'bridge' | 'ford' } | null;  // viaFord re-roots here (R2)
  rank: Rank;                    // town 0, village 1, rest 2
}
export interface TheaterEdge {
  id: number; a: number; b: number;      // polyline runs a -> b
  kind: 'road' | 'rail';
  moveClass: MoveClass;
  polyline: Vec[];
  lengthM: number;               // integer metres along polyline; >= MIN_EDGE_M
  paceMpm: number;               // baked: MOVE_MPM[moveClass] * length-weighted region pace mult (R3)
  rank: Rank;                    // highway 0, road 1, track 2
}
export interface Region {
  id: number;
  polygon: Vec[];  holes?: Vec[][];
  centroid: Vec;   bbox: { x0: number; y0: number; x1: number; y1: number };
  areaM2: number;
  terrainClass: TerrainClass;
  name: string;
  seatNodeId: number | null;     // naming + derived-control anchor
}
export interface River { id: number; name: string; polyline: Vec[]; widthClass: 'stream' | 'river' }

export interface Theater {
  version: number;               // === THEATER_VERSION at generation; persisted via CampaignSpec.genVersion
  seed: number;
  name: string;                  // '{principal town} sector'
  boundsM: { w: number; h: number };   // default 24000 x 18000
  nodes: TheaterNode[]; edges: TheaterEdge[]; regions: Region[]; rivers: River[];
  objectiveNodes: number[];      // semantics owned by WarGoals (section 4)
  sources: Record<Side, number[]>;  // supply source nodes; validated non-empty IF supply ships (OQ4)
}

export type NetPos =                                            // R1: metres, tagged
  | { kind: 'node'; nodeId: number }
  | { kind: 'edge'; edgeId: number; s: number /* metres from edge.a */; dir: 1 | -1 };
```

**Ownership** (Front V2, not Theater): `controlByNode: (Side | null)[]` indexed by node id. Arrival at a node with no live enemy force paints it unconditionally (today's entry-paint rule, preserved deliberately — hold/garrison requirements belong to the ZOC proposal, OQ11). Edge control is derived: both endpoints same side → that side, else CONTESTED. Region control derives from the seat node. The contested-edge set IS the front line as data — the structure the recon says never existed.
Rejected: per-region ownership (a force marching one edge must not flip 8 km of countryside); persisted edge control (derivable, doubles save surface, can disagree after load).

**Force** (Front V2; merges realtime + AI + realism fields; realism fields exist only if the owner selects the system — dead fields are deleted, not carried):

```ts
export type ForceRole = 'line' | 'garrison' | 'reserve';        // R5; kills the 'Reserve' name-string
export interface Force {
  id: number; side: Side; name: string;
  pos: NetPos;
  path: number[];                // remaining EDGE ids (parallel road/rail disambiguation)
  dwellMin: number;              // ford/bridge dwell elapsed
  strength: number; companyIndex: number;   // blue roster / red counter — unchanged contract
  role: ForceRole;               // replaces name-match and holds()-by-objective-cell
  engagedIn: number | null;      // CoarseBattle id
  queuedAt: number | null;       // bridge defile queue
  // conditional on OQ4: fatigue: number; stance: 'march'|'screen'|'rest'; untracedMin: number;
}
export interface TheaterSides { blue: 'human' | 'ai'; red: 'human' | 'ai' }  // first-class; replaces ?ai= for invariants
```

The front clock stays a minute-granular sim clock. "Real-time" = continuous positions advanced per strategic minute at `SPEEDS` multipliers — the accumulator loop shape in `src/main.ts` is unchanged.

## 2. Procedural generation

`makeTheater(seed, cfg: TheaterConfig) => { theater, initialControlByNode }`. Pure. Throws `TheaterGenError` after 8 attempts (attempt base mirrors `generateMap`: `mulberry32((seed ^ THEATER_SALT) + attempt * 0x9e3779b9)`). NEVER returns a fallback theater.

**Stage order, frozen tags 40-59 (append-only; bourg owns 1-16, relief 20-29):**
T_RIVER(40) main river + 2-3 tributaries → T_TOWNS(41) settlements (towns prefer crossings/confluences; villages spaced-sample) → T_ROADS(42) hierarchy connecting settlements; every road-river intersection mints a bridge/ford node → T_CROSSINGS(43) crossing audit (bridge-count band) → T_RAIL(44) optional line + halts (OQ9) → T_REGIONS(45) jittered-grid nearest-site partition + terrainClass paint (integer-only, no Voronoi lib — bourg precedent) → T_NAMES(46) Norman toponym grammar, per-site draws keyed on imul-hash of node pos, never array index (interiors D9) → T_OBJECTIVES(47) objectives + supply sources + initial front (river-anchored partition; the `frontX` successor). Validation draws ZERO rng.
Rejected: roads-first (junction-flavoured towns, arbitrary river crossings); regions-first (doubled constraint satisfaction for invisible gain).

**Plausibility bands (default 24×18 km preset; scale with cfg):** towns 3-5 (spacing ≥ 5000 m, ≥ 2 river-adjacent), villages 8-12 (≥ 1800 m), main-river bridges 2-4, fords 0-2, 1-2 highways, mean degree 2.6-3.2, nodes 35-60, edges 50-90, regions 25-40; area mix farmland 30-45%, bocage 25-40%, forest 10-20% (1-3 massifs), marsh 3-8% (river-adjacent only), settlement 3-6%. `MIN_EDGE_M = 1200` enforced (R21).

**Named reject reasons** — ELEVEN unconditional (each constructible in tests, each THROWS): `disconnected`, `no-objectives` (closes the `operationStatus` permanent-'ongoing' stall), `objectives-unreachable`, `crossing-starved` (<2), `crossing-flooded` (>5), `front-degenerate` (either side <25% of nodes), `region-sliver` (<250,000 m²), `orphan-node`, `spacing`, `name-collision`, `short-edge` (< MIN_EDGE_M). A TWELFTH, `no-supply-source`, is added by the supply lane (S50) and exists only if the owner selects supply (OQ4) — it is not in S11's gate. `TheaterGenError.knob` maps reason → likely `TheaterConfig` field for the reject card (R12).

**Gates:** byte-identical regeneration from (version, seed, cfg) — 16-seed full-structure hash; D2 stage-isolation test (retune one stage, other stages' hashes unmoved); perf per R11 — TARGET 30 ms mean / 80 ms max over 200 seeds measured standalone by `scripts/theaterperf.mjs`, CI ASSERT 66/180 min-of-reps in `tests/theater-perf.test.ts`; ≤ 1% first-attempt rejects; `THEATER_VERSION` bump test fails loudly when any pinned hash moves without a bump (`scripts/theater-fp.mjs` prints hand-pasteable rows — the relief-wiring PRE_RELIEF discipline, no `-u` laundering).

## 2.5 Initial disposition — the order of battle

`makeTheater` emits geography and `initialControlByNode`. It never emits forces: the Theater is immutable and force state lives in Front V2 (§1). The campaign-start order of battle is a separate pure function, and it is the V2 replacement for `newFront` in `src/strategic/bridge.ts` — today's sole disposition function, which hardcodes three blue company chits and five named red garrisons at fixed strengths on fixed cells.

```ts
// src/strategic/theatergen/disposition.ts
export function makeDisposition(
  theater: Theater,
  cfg: CampaignConfig,
  rng: Rng,               // specStream(spec, SPEC_TAG.DISPOSITION) — frozen tag 3
): { forces: Force[]; establishment: Record<number, number> };
```

- **Blue.** `cfg.blueCompanies` (2-4) line forces, one per company, placed on blue ENTRY NODES — the blue-side nodes of the T_OBJECTIVES front partition with the highest road rank, sorted by node id, cycled if companies outnumber entry nodes. `companyIndex` maps to the roster in generation order, so `src/campaign/campaign.ts newCampaign(seed, blueCompanies)` becomes parameterised: `COMPANY_NAMES` grows to a frozen four-name list (`Able | Baker | Charlie | Dog`) and `newCampaign` takes the first `blueCompanies` of it. That file is in S13a's list.
- **Red.** Garrison count and strength scale from `cfg.redStrength` (0-4) across `theater.objectiveNodes` plus crossing nodes, `role: 'garrison'`, strengths drawn on the DISPOSITION sub-stream inside a stated band. Red mobile forces (`role: 'line'` / `'reserve'`) come from the same knob — a goal-driven red with only garrisons cannot attack (§4).
- **Establishment** is recorded per force at creation. It is the denominator of the §8.7 strength bar; the `/27` constant dies with it.
- **`syncStrengths`** (bridge.ts) — the blue roster ↔ `Force.strength` mirror, called on every day roll and after every battle — ports verbatim onto `Force[]` keyed by `companyIndex`. It is not deleted, it is re-rooted, and it is in S13a's file list.
- **Named rejects** (THROW, never silently place): `no-entry-node` (the blue partition holds no node of road rank ≤ 1), `garrison-starved` (`redStrength > 0` yet fewer garrisonable nodes than the band floor), `establishment-zero`. These are disposition rejects, not theater rejects — a valid theater can still fail a disposition, and the customize screen names the CampaignConfig knob, not the map knob.
- **`MAX_FORCES = 24`** is asserted HERE and on the `addForce` path (§3.3), not at generation — `makeTheater` never sees a force.

## 3. Real-time movement + engagement lifecycle

**3.1 Movement.** Per strategic minute an unengaged, unqueued force advances `paceMpm` metres along its current edge. Constants: `MOVE_MPM = { highway: 66.7, road: 50, track: 33.3 }` m/min; road:track = today's `CELL_MINUTES` road:open (10:15). The forest pace mult is 0.5, applied to the moveClass base, and the pinned 3:1 road:woods ratio is reproduced by TRACK × FOREST only: 33.3 × 0.5 = 16.65 m/min against road 50. A ROAD through forest is 25 m/min — 2:1, deliberately, because a metalled road through woods is not a forest track and today's grid could not express one (a cell is road terrain OR woods terrain, never both). The 3:1 figure is a track-class claim; do not restate it as a whole-class invariant.
`FORD_CROSS_MIN = 45` node dwell reproduces today's ford premium exactly (`CELL_MINUTES` river 60 − open 15 = 45), so a ford beats any detour longer than 45 minutes of road and loses to a bridge inside it — the INDEX.md 2026-07-23 river-fords rule ("Dijkstra never fords while a bridge is in reach, but a mid-band ford beats a 10+-cell detour"). That equivalence is the S13 gate. `forceEtaMinutes` mirrors the step arithmetic exactly — the pinned `chitEtaMinutes` lockstep-mirror rule carries over as a test. Dijkstra over ≤ 60 nodes, linear-scan is fine (3.6k ops vs 1.44M today).

**3.2 Contact.** `graphGap(a, b)` returns metres when co-located on the graph (same edge / same node / edge+incident node / two edges sharing a node), else Infinity. Contact fires at `graphGap <= CONTACT_M = 300`. Forces on parallel non-incident roads never fight — the negative the grid could not express. Rejected: contact at node arrival only (head-on columns pass through each other); closing-velocity test (unneeded — equal-speed same-direction never closes).

**3.3 Step.** `step()` = clock++ → resolve battles with `endMin <= clock` (ascending id) → advance ALL unengaged forces → detect contacts over final positions (pairing lower-id-first, deterministic) → return `TheaterEvent[]`. The one-engagement-per-minute short-circuit is deliberately dropped (recon names it an array-order bias the pin encodes; the pin re-baselines regardless). ONE force number governs: `MAX_FORCES = 24` (typical live count 6-16 across both sides). It is asserted on the two paths that create forces — `makeDisposition` (§2.5) and `addForce` — never at generation, because `makeTheater` never sees a force. O(24²) = 576 pair tests per simulated minute; the ×60 speed multiplier makes that 34.6k pair tests per real second, budgeted in §8.11.

**Day roll.** The existing beat in the `src/main.ts` strategic tick is preserved VERBATIM, in order: `front.day > prevDay` → `advanceDays(campaign, …)` → on `front.day % REINFORCE_CYCLE_DAYS === 0` (=2) `fillReplacements(campaign, front.day * 31 + 7, REINFORCE_PER_COMPANY)` (=12) → `syncStrengths(campaign, front)` (§2.5) → autosave. Replacements are SUPPLY-INDEPENDENT at launch: §5(a) puts replacement throttling out, which means the cycle and the per-company count do not read supply tier at all — not that replacements stop. `minutesToReinforcement` (src/strategic/front.ts) survives as a HUD read and moves into the DOM chrome in S30.

**3.4 Timed coarse battles.** `CoarseBattle { id, site, attackerId, defenderId, joined, startMin, endMin, forced }`. `durationMin = min(240, 45 + 1.4 × min(atk, def))`; trivial mismatch collapses to 15. The coefficient is derived from the MEASURED strength domain, not picked: `newFront` fields red garrisons at 36/109/36/109/109 and blue companies at 138 (pinned in tests/strategic.test.ts), so `min(atk, def)` lives in [36, 138] and the range spans 95-238 minutes — a walkover and a grind differ by 2.5×. A 0.5 coefficient would have collapsed the whole range to 63-114 min, which is failure mode (B) of OQ12 wearing a formula. There is no lower clamp arm: `min = 0` is impossible for a live force, and the only sub-95 duration is the trivial-15 collapse. The 240 cap is live and load-bearing — reinforcement joins ADD strength, so `min(atk, def)` passes 139 in a contested stack and the cap is what stops a two-corps grind from pinning both sides for a day. Participants are PINNED (`engagedIn`): no movement, `orderMove` rejects `'engaged'`. At `endMin` the existing `resolveCoarse` runs — arithmetic untouched (the tuned Lanchester chain is the asset). RNG salt draws at `startMin`, so a mid-battle save resumes identically. Pinning makes concentration real (a pinned defender cannot reinforce elsewhere) — the lever the goal-driven AI needs; the AI must also value breaking contact, or the player discovers fix-and-bypass first (planner ladder, section 4).
**Reinforcement joins** the existing battle: strength adds, `endMin` recomputes floored at now+15, and the `forced` flag RE-EVALUATES via `trivialMismatchWinner` — a 5:1 walkover reinforced to 2:1 loses its guaranteed winner. Rejected: second concurrent battle at one site (double-counts the defender).

**3.5 Stacking.** Friendlies pass and co-occupy freely (frontage is OQ4's ZOC lane). ONE exception: bridge nodes have defile capacity 1, `BRIDGE_DWELL_MIN = 15`, FIFO queue at `s = lengthM - 1`. Deadlock impossible: opposed forces at one bridge are within CONTACT_M first.

## 4. Strategic AI

**4.1 Two-tier planner** (`src/strategic/planner.ts` + rewritten `src/strategic/command.ts`).


Resolution ladder: crossing-assault classes first (crossing node + attacker's approach bank — `bridge-assault` / `ford-assault`), else node kind (`town → settlement`, `village → hamlet`), else containing/nearest region's terrainClass (`forest→forest`, `marsh→marsh`, `farmland|bocage→farmland`, `settlement→settlement`), with `roadside` for mid-edge fights on highway/road through farmland.

Today's table: settlement→`'bourg'`, hamlet→`'open'`, forest→`'woods'`, farmland→`'open'`, marsh→`'open'`, roadside→`'road'`, bridge-assault→`'bridge'`, ford-assault→`'river'` (preserves the `viaFord` map override). `makeStrategicBattle` consumption: `generateMap(seed, 320, 240, BATTLE_CLASS_TO_MAPKIND[battleClass], { interiors: true })`; battle name from theater toponyms, never coordinates; seed = un-xor'd `(clockMin*7919 + siteKey)`; `resolveCoarse` seed = campaign-xor'd same shape (R4).

**`resolveCoarse` re-root — the whole function, not just its salt.** The grid's removal touches four things inside `resolveCoarse` beyond `siteKey` and `COARSE_DEF_MULT`, and all four are S16 gates:
1. **Two clocks become explicit parameters, both bound to `startMin`.** Today the function reads `front.clockMin` twice: once inside the salt `(c.seed ^ (front.clockMin * 7919 + e.cell)) >>> 0` and once inside the terrainMult chain via `lightAt(front.clockMin)`. **9.2 CampaignSpec** (`src/campaign/spec.ts`) — the persisted, shareable unit, and the SAME object the generator consumes (R10):
`CampaignSpec { genVersion, seed, seedText, theater: TheaterConfig, campaign: CampaignConfig }`.

`TheaterConfig` (reaches `makeTheater`): `sizeKm: 18|24|32` (R17), riverDensity **1-3**, crossingScarcity 0-2, roadDensity 0-3, railDensity 0-2, townDensity 1-6 per 100 km² **capped by `townSpacingMinKm`**, townSpacingMinKm 2-5, terrainMix enum, woodsShare **1-4**.

`CampaignConfig` (structurally unable to reach the generator — a war-length change must not move the map): warDays 7|14|21|30 subject to `minWarDays(sizeKm) = { 18: 7, 24: 14, 32: 21 }` (R17), victory preset, blueCompanies 2-4, redStrength 0-4, redDoctrine enum, plus the owner-selected realism toggles (R25). `warDays` is the value `OP_DEADLINE_DAYS` becomes; `makeWarGoals` (§4.2) consumes it; `blueCompanies` and `redStrength` are consumed by `makeDisposition` (§2.5) and by nothing else.

**Invalid combinations DO exist — there is a feasibility precheck.** Expressing quantities as densities does not make the cross-product feasible, and three combinations against §2's bands are provably impossible:
1. townDensity 6 on the 24×18 km default asks for 26 towns, but townSpacingMinKm 5 needs ≈ 21.6 km² per town under hexagonal packing = 562 km² against 432 km² available — every seed rejects on `spacing`.
2. riverDensity 0 mints no river, so no road-river intersection mints a crossing node in T_ROADS and `crossing-starved` (<2) always fires. Hence the union floor of 1.
3. woodsShare 0 cannot satisfy the forest 10-20% area band. Hence the union floor of 1.
Two mechanisms close this. (i) The §2 bands are FUNCTIONS of cfg, not constants: town count follows `townDensity × areaKm2 / 100` and the spacing band relaxes with it, so the two knobs move together instead of fighting. (ii) `feasible(cfg): { ok: true } | { ok: false, knob, reason }` is a pure precheck the customize screen calls on every knob change; an infeasible point greys out Generate & Play with the offending knob NAMED, and `deadline-infeasible` is its `CampaignConfig` arm (warDays below `minWarDays(sizeKm)`). This is a visible state, not a silent clamp.

Sub-streams: `SPEC_TAG = { THEATER:1, ROSTER:2, DISPOSITION:3, AI_SALT:4 }`, frozen — changing town density never renames the men.

## 10. Battle deployment phase

Pre-first-unpause placement inside a deployment zone. AI staging is FROZEN (its staging IS the zone anchor; changing it re-records the balance grid — held line).

- **Zone = tile mask, not a rectangle**: `(role geometry) ∪ slack discs (8 m) around every own auto spot`, AND passable, clipped to the y gutter. "Auto placement is always legal" is structural: bridge.ts stages defenders on `GARRISON_RADIUS = 45` anchors that sit at x=18-30 on bourg maps — a flat 50% band would outlaw the game's own staging. Role geometry: attacker strip `x <= west.x + DEPLOY_ATK_DEPTH` where **`DEPLOY_ATK_DEPTH = 12` is declared INDEPENDENTLY of `ATTACK_POST_MARGIN = 32`**. The two constants are deliberately distinct because they are not the same quantity. `ATTACK_POST_MARGIN` is an OBJECTIVE FILTER line: bridge.ts uses it only as `beyondDeploy = plan.objectives.filter(o => o.x >= west.x + ATTACK_POST_MARGIN)`, with its own comment recording that bourg maps place outpost objectives at x=18-30 and that legitimate first objectives start at x ≥ 43. `DEPLOY_ATK_DEPTH` is a PLACEMENT DEPTH, measured from the actual staging band: `makeStrategicBattle` stages the attacker at `west.x + 3` (support) and `west.x + 7`, and `west.x = 3` is fixed by both `generateMap`/`spawns` and `bourgSpawns`. So the real staged depth is ~7 tiles, and 12 is 7 plus a small forward allowance. Binding the depth to 32 would have made the strip `x <= 35` — which CONTAINS the x=18-30 outpost objectives the filter deliberately excluded, letting the player deploy a rifle squad straight onto an outpost and take it before contact. That is the exact walk-in win `ATTACK_POST_MARGIN` exists to close. Two gates hold the separation: a test asserts `DEPLOY_ATK_DEPTH < ATTACK_POST_MARGIN`, and no point in the attacker zone lies within `GARRISON_RADIUS` (45 m) of any objective that `beyondDeploy` excluded. Defender = objective discs `DEF_R = 70` (45 + one hedgerow parcel; per-kind Partial overrides bourg 60 / woods 80 — deliberately Partial, never a fifth exhaustive MapKind Record); ford-attacker = slack discs only (a force caught mid-crossing did not choose its ground — doctrine made visible, not skipped); meeting = own entry strip (dark until the realtime lane produces both-sides-moving contacts).
- **Placement = pre-tick teleport through `resolveMoveSpots`** (`src/sim/spots.ts` — pure, zero rng): the placement gesture builds the same `SpotQuery` an order builds, resolved spots write `s.x/s.y/s.level` directly. sim.rng stream position is untouched (tested against a twin sim). Emplacements move as a pose (crew re-seated by the `addEmplacement` OFFSETS loop), state stays `'deployed'`, stockpile untouched. Auto-deploy default: committing an empty placement is ZERO mutations — "touch nothing and press Start" is byte-identical by construction, because tests and `scripts/balance.mjs` call `makeStrategicBattle` directly and never enter the phase (R19).
- **Flow**: contact → modal [Attack | Auto-resolve | Stand down (attacker path only)] → DEPLOY → Start → battle. The deploy screen has EXACTLY ONE exit (Start). No stand-down, no auto-resolve, no back — a withdraw button here would be the 50e5b2e veto wearing a different hat, reachable on the defender path where the modal deliberately offers none. Ceremony is answered upstream: a battle the player will coarse-resolve never reaches deploy.
- **AI staging stance**: unchanged, no AI zone object (its staging derives the zone); a validation-only test may assert AI spots against a mirrored zone (OQ21). AI deployment doctrine is a later lane.
- **Determinism posture**: no mid-deploy save (consistent with no battle save); on commit a `DeployPlan` dump (`__game.getDeployPlan()`) keeps a battle reproducible from (seed, clockMin, chits, plan). `?deploy=0` auto-commits. Every `PlaceReject` (`outside-zone | no-footing | occupied | unreachable | no-stairs`) renders a specific banner sentence; degenerate zone places what fits and says so ("the position holds only N of M men").
- **Harness blast radius**: `gotoStaged` calls `commitDeploy()` in the SAME commit as the first visible deploy UI; sweep gains a preflight assertion (`deployState() === null`) modelled on the hour pin; gate = all 112 baselines byte-identical; demo.mjs gains one deliberate new deploy beat.

## 13. Open questions for the owner — consolidated

Settled owner decisions are not re-asked. Each question: options, then the recommendation.

**OQ1 — OWNER GATE, migration: what happens to a v3 save?** (a) plain clean break — key bump + message, ~25 lines cheaper; (b) clean break + roster carry-over — `adoptLegacyRoster` keeps the named men/wounds/bonds/diary, war restarts day 1 on a new theater; (c) legacy read-only loader — forks all of src/strategic to view a campaign nobody can continue. **Recommend (b)** — full argument in section 7.

**OQ2 — Player-contact tempo.** (A) hard pause, today's behaviour — simple, but pause frequency goes UP with a multi-axis attacking AI; (B) pin + queue: contact pins both forces, theater runs, inbox card, grace expiry HARD-PAUSES (never auto-resolves), first contact of a campaign hard-pauses; (C) pocketed tactical sub-clock — unbounded failure mode (the AI can end the war while you fight), would not ship. **Recommend (B).** Worst case degrades into exactly (A).

**OQ3 — Does a fought fine battle cost theater time?** (A) free, today — but once coarse battles are timed, always-fight strictly dominates (a real exploit); (B) bounded catch-up: on debrief return, step the theater by the same durationMin (≤ 240 min) the coarse resolver would charge, every event logged; (C) pin participants without catch-up — the rest of the front freezes anyway. **Recommend (B)** — the only option where fine and coarse cost the same, keeping Auto-resolve an honest choice.

**OQ4 — Realism menu (the menu question): which systems ship in V2?** Per section 5: supply (two effects, degrade-only), FOW (contact model + screen stance, symmetric), fatigue, ops-tempo (doctrine + ETA halves; night NUMBER later) — with ZOC wave 2, edge capacity out, supply attrition out. Alternatives: three-without-FOW (cheapest, but a second AI re-tune later); two free ones only (ships the graph as decoration — the failure owner decision 1 forbids). **Recommend all four as scoped**, with the hard condition that `IntelView` is the only AI read surface regardless of the pick.

**OQ5 — Which realism systems are player-facing setup toggles?** (a) three: `supply`, `recon: omniscient|contacts`, `nightTempo` — each has a legible off-state and an existing seam; (b) five incl. fatigue + ZOC — 2⁵ unmeasured balance branches; (c) none. **Recommend (a).** Any system made unconditional loses its CampaignSpec field before S40 freezes the share layout.

**OQ6 — Does the AI play under the same fog?** (A) identical fog and detection; (B) doctrine-level intel advantage as a difficulty dial; (C) AI omniscient behind the accessor. **Recommend (A)** — (C) is the exact asymmetry the tactical FoW decision was written to kill; (B) is a legitimate future dial the accessor makes one line.

**OQ7 — `coarseNightMult` value timing.** (A) stays exactly 1.0 through V2; measured later as its own change + own re-baseline; (B) fold into the V2 re-freeze — unattributable; (C) drop the hook. **Recommend (A).** Direction when measured: below 1.0.

**OQ8 — Village (hamlet) coarse defence multiplier.** (a) uniform ×7 — 8-12 villages make the whole map a fortress; (b) town ×7 / village ×3.0, one new knob tuned in the S59 sweep; (c) continuous from area — uninspectable. **Recommend (b)**; the re-baseline is the free moment to add it.

**OQ9 — Rail at launch.** (a) geometry only (line + halts render and are named; tag frozen; zero gameplay); (b) cut; (c) full rail movement/supply. **Recommend (a)** — cheapest "real theater" signal; gameplay waits on the supply decision.

**OQ10 — Theater scale.** (a) 24×18 km default, knob {18, 24, 32}; the DEFAULT deadline stays 14 days at 24 km (~8 h road transit preserves the tuned pacing within noise), but `OP_DEADLINE_DAYS` stops being a module constant and becomes `CampaignConfig.warDays` with the size floor `minWarDays = { 18: 7, 24: 14, 32: 21 }` — a 7-day war on a 32 km theater is unwinnable and `feasible(cfg)` rejects it by name rather than shipping it (§9.2, R17); (b) 32×24 epic — empty marching days + doubled AI surface; (c) 20×15 parity — cramped, buys nothing since the pin re-baselines anyway. **Recommend (a).**
